## ① 多窗口协调（D18/D19）— 重要

**验证什么**：窗口 A 是宿主（跑子进程），窗口 B 应当从机（不重复 spawn）；A 关闭后 B 接管。

**为什么重要**：这是多窗口单例 + 心跳接管的核心机制，日常多窗口用 VS Code 时必触发。

### 步骤

1. **开窗口 A**（任意 workspace）。看状态栏：应显示 `代理:本窗口运行`。Output（Claude Code Proxy 频道）有 `成为宿主，代理子进程在 127.0.0.1:11434 运行（pid=XXX）`。
2. **开窗口 B**（另一个 workspace，或同 workspace 新窗口）。看状态栏：应显示 `代理:其他窗口运行`（**不是**「本窗口运行」）。Output 有 `端口已被占用（别的窗口已起代理），本窗口作为从机` 或类似（注意：新架构下 B 不会 spawn 子进程，因为 tryBecomeHost 先 healthz 探测，通了就 return）。
3. **确认 B 没多起子进程**：任务管理器里只有一个 Code.exe 子进程监听 11434（pid 与 A 的 Output 一致）。
4. **关窗口 A**（正常关闭，触发 deactivate）。A 的 Output 应有 `扩展卸载，停止本窗口代理`。
5. **等 2-3 秒**，看窗口 B：状态栏从 `其他窗口运行` 变成 `本窗口运行`。B 的 Output 有 `探测到代理不在，尝试接管` + `成为宿主，代理子进程...pid=YYY`（新 pid）。

### 预期 ✅
- A 开着时，全局只有一个子进程（端口单例）
- A 关闭后，B 2s 内接管，新子进程 pid 不同

### 异常表现（如果出问题）
- [ ] B 也 spawn 了子进程（端口冲突，两个都起不来或一个 EADDRINUSE 退出）→ 记录
- [ ] A 关闭后 B 没接管（状态栏一直「其他窗口运行」但实际没进程）→ 记录
- [ ] A 关闭后 B 接管超过 5s → 记录

## ② EADDRINUSE 退化（端口被无关进程占）— 低优先

**验证什么**：11434 被一个**非插件子进程**占用时，插件的行为（是否刷屏、状态栏表现）。

**为什么低优先**：边缘场景，正常使用端口要么插件自己占、要么空闲。

### 步骤

1. 用一个占位进程占住 11434：
   ```
   node -e "require('net').createServer().listen(11434,'127.0.0.1',()=>console.log('holding 11434'))"
   ```
   （保持这个进程运行）
2. 重新加载 VS Code 窗口（让插件 activate）。
3. 观察 Output 1 分钟：插件会反复尝试 spawn 子进程，子进程 EADDRINUSE exit(1)，心跳 re-spawn。
4. 看状态栏：应显示 `代理:未运行` 或 `检测中…`。

### 预期 ✅
- 插件不停尝试但每次失败（子进程 EADDRINUSE exit(1)）
- 状态栏不显示「本窗口运行」（因为没成功 listen）
- 日志有一定重复（每 2s 一次心跳尝试），但**不应疯狂刷屏**（每次 spawn 失败应有 5s 间隔，因为 waitForPortReady 超时 5s）

### 异常表现
- [ ] 日志疯狂刷屏（每秒多条）→ 记录频率
- [ ] 状态栏错误地显示「本窗口运行」→ 记录
- [ ] 插件卡死/无响应 → 记录

### 清理
- Ctrl+C 停掉占位进程，观察插件是否 2s 内自动接管（spawn 子进程，状态栏变「本窗口运行」）。

## ③ stdio 大量输出不阻塞 — 低优先

**验证什么**：子进程 stdout 输出大量日志时，OutputChannel.appendLine 是否会阻塞子进程的 stdout 管道。

**为什么低优先**：正常用 LLM 代理，每个请求才几行 concise 日志，不会触发。只有极端高压（每秒几十请求）才可能。

### 步骤（可选，难触发）

1. 插件正常跑（窗口 A 是宿主）。
2. 用脚本并发打代理发请求，触发大量 trace 日志：
   ```
   for i in $(seq 1 100); do
     curl -s http://127.0.0.1:11434/v1/messages -H "x-api-key: t" -H "content-type: application/json" \
       -d '{"model":"x","max_tokens":1,"messages":[{"role":"user","content":"hi"}]}' > /dev/null &
   done; wait
   ```
3. 观察代理子进程是否还活着、响应是否正常、Output 日志是否完整。

### 预期 ✅
- 100 个请求都返回（502 也算正常，因为没配上游）
- 子进程不卡死（之后 healthz 仍通）
- Output 日志不丢行

### 异常表现
- [ ] 子进程卡死（healthz 不通）→ 记录
- [ ] Output 日志丢行/乱序 → 记录

## ④ re-spawn TIME_WAIT（反复 kill/重启）— 中优先

**验证什么**：反复 kill 子进程让它 re-spawn，看端口会不会因为 TIME_WAIT 冲突导致 re-spawn 失败。

**为什么中优先**：你已测过 2 次 re-spawn 正常，但反复多次（10+ 次）可能出现 TIME_WAIT 累积。

### 步骤

1. 插件正常跑（窗口 A 宿主），记下当前子进程 pid。
2. 在任务管理器里杀掉这个子进程（或用 `taskkill /PID <pid> /F`）。
3. 等 2-3 秒，看 Output 有 re-spawn 日志 + 新 pid。
4. **重复 10 次**（每次杀新 pid）。
5. 第 10 次后，确认状态栏仍 `本窗口运行` + healthz 通。

### 预期 ✅
- 每次 kill 后 2-3s 内 re-spawn 成功
- 10 次后仍正常，端口没冲突

### 异常表现
- [ ] 第 N 次 re-spawn 失败（端口被占，子进程 EADDRINUSE 退出，无法恢复）→ 记录第几次、pid
- [ ] re-spawn 间隔越来越长 → 记录
